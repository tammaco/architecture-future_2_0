# Задание 3. Проектирование целевой архитектуры и оценка рисков внедрения

1. Целевая [архитектура](https://github.com/tammaco/architecture-future_2_0/Task3Advanced/Будущего 2.0.drawio) системы «Будущего 2.0» в горизонте трёх лет.

2. Карта рисков трансформации

2.1. Архитектурные риски

|Риск|Вероятность|Влияние|Описание|
|-|-|-|-|
|Деградация производительности запросов|Высокая|Высокое|В новых Lakehouse-архитектурах сложные JOIN-ы могут работать медленнее, чем в монолитном SQL-движке|
|Болото данных|Средняя|Высокое|Без строгой политики метаданных и качества данных хранилище S3 превратится в болото|
|Сложность обеспечения консистентности|Высокая|Высокое|При переходе от ACID-транзакций к событийной модели возникают риски рассогласования данных|
|Утечка данных между доменами|Низкая|Критическое|Медицинские и финансовые данные требуют строгой изоляции; при неправильной настройке прав доступа возможна их утечка|

2.2. Организационные риски

|Риск|Вероятность|Влияние|Описание|
|-|-|-|-|
|Сопротивление команды изменениям|Высокая|Среднее|Переход с SQL на Python/dbt/Kafka требует переобучения|
|Потеря экспертизы по легаси|Высокая|Среднее|Знания уходят вместе с сотрудниками, миграция бизнес-логики становится рискованной|
|Распыление ответственности|Средняя|Высокое|В децентрализованной Data Mesh-архитектуре домены могут начать трактовать данные по-разному, теряя единое представление|

2.3. Технологические риски

|Риск|Вероятность|Влияние|Описание|
|-|-|-|-|
|Нестабильность Kafka|Средняя|Высокое|Отказ центральной шины парализует все интеграции и потоковые витрины|
|Ошибки в миграции данных|Высокая|Высокое|При переносе 100+ ТБ данных возможны потери или искажения|
|Зависимость от облачного вендора|Средняя|Среднее|Перевод в облако создает риски, связанные с изменениями тарифов или политик провайдера|

3. План управления рисками

3.1. Технические меры

- **Для деградации JOIN-ов**: Использовать материализованные представления в Iceberg с денормализацией и тестировать производительность на пилотных витринах до полного переезда

- **Для «болота данных»**: Внедрить каталог метаданных с первого дня, поддерживать его актуальность

- **Для консистентности**: Разработать и стандартизировать паттерн Saga для длительных транзакций и идемпотентные обработчики событий, чтобы избежать дублирования

- **Для Kafka**: Развернуть Kafka в отказоустойчивой конфигурации (3+ брокера) в разных зонах доступности с настроенным мониторингом

- **Для утечек данных**: Внедрить строгую авторизацию на уровне API Gateway и в Trino, использовать шифрование

3.1. Управленческие меры

- **Для сопротивления команды**: Внедрить программу обучения, начать с пилотного проекта в одном домене, чтобы команда получила быстрый позитивный опыт .

- **Для потери экспертизы**: Провести инвентаризацию бизнес-логики в старом DWH до начала миграции. Все критичные хранимые процедуры должны быть задокументированы (ADR) и переписаны на новой платформе с участием экспертов по легаси

- **Для распыления ответственности**: Назначить владельцев данных для каждого домена, ответственных за качество и интерпретацию данных

- **Для ошибок миграции**: Использовать стратегию Strangler Fig Pattern. Новые сервисы запускаются параллельно со старыми, бизнес-пользователи постепенно переводятся на новую систему
